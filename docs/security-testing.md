# Security regression evidence

The separate `Security regressions` workflow has mandatory Linux and Windows tiers. It supplements ordinary portable/native document tests, CodeQL and dependency checks; none replaces a full source-and-runtime security engagement.

The finite scenario ledger is [tests/security/coverage.json](../tests/security/coverage.json), with fixture/control/containment documentation in [tests/security/README.md](../tests/security/README.md). It covers package relationship case identity, output links including native Windows/Python 3.11 junctions, shared HTML parser work admission across callers, and bounded TeX output observations. Independent WindowsBase OPC observation is not a claim about Microsoft Word behavior.

Prepared runtimes and trusted kernel probes precede reviewed document/helper execution. Windows authority checks protect the target, toolchain, parent-owned paths, scratch-root boundary and volume/quota controls. A unique CI-owned AppContainer profile is resolved through native APIs; its real filesystem and virtual-registry storage must be sealed before admission, tested for mutation denial and deleted during owned cleanup. Profile registration does not authorize writable off-scratch storage. Registry sealing must preserve read access while independently denying value writes, subkey creation, deletion, DACL changes and ownership changes; composite write-rights masks cannot be treated as mutation-only. Exact final-token open-only positive/negative controls precede resume, and matching stored descriptors alone are not effective-access evidence. A child changing permissions on its own scratch file is not an escape: protected-creator and owner-selection controls must still prove that no protected resource or storage limit can be bypassed. Restricted-primary-token construction must remove Administrators ownership eligibility before LPAC admission; the actual suspended worker and descendants are checked again, and a native owner-assignment negative control must reject that identity even on a private file with `WRITE_OWNER`. Deny-only attributes alone do not satisfy this gate, and every remaining owner still requires a finite persisted quota. This construction remains a candidate until exact-revision hosted controls pass. Access-checked query denial on the worker's own process/thread is repaired only on those two objects, using its exact user plus existing package grant; same-token negative/positive controls and unchanged owner/group/integrity-label readback precede resume. This does not widen protected-storage access or establish a unique DLL initialization cause. Logical per-owner quota and physical aggregate capacity are verified separately, including sparse-file cases. Any missing isolation control fails closed, without executing the target phase. Required native cases cannot be converted into green skips. Tiny authored fixtures and dummy sentinels are the only test data; no credentials, deployed endpoints, stress payloads or real user manuscripts are needed.

## Evidence boundaries

- A requested container option is not an observed kernel control.
- A mock reparse attribute is not a native junction result.
- A case-insensitive package API is not proof of every Office consumer.
- An outer scratch quota is not production TeX output-bind quota.
- A mechanical result, artifact hash or clean CI is not user consent or semantic translation approval.

A bounded native startup trace of fixed trusted Python `-c pass` is diagnostic phase evidence only. It uses the same isolation settings and no target imports; normal undebugged kernel preflight remains the sole admission gate. A fixed no-CRT native `ExitProcess(0)` fixture provides an image-independent differential under those same controls; existing hosted compiler tools, bounded PE/import validation and a read-only seal precede its launch. This diagnostic cannot replace Python 3.11 or admit target code. Debugger-altered behavior, either diagnostic exit or a last-loaded DLL never establishes containment or a unique initialization cause. A failed profile-access control can also record bounded API-handle granted-rights and same-mask fresh-open metadata; native query failure remains unknown, and these diagnostics never change the rejected control's outcome.

Only the exact tested revision, actual prerequisite observations, load-bearing positive/negative assertions and owned cleanup support a completion claim. Source-audit hypotheses remain unresolved until their decisive facts are observed or independently refuted. All limits must be named in the job/report rather than hidden by `continue-on-error`.

## Diagnostic logs

Parent controllers write one UTF-8 UTC log per run, without document bodies or secret values. Linux uses `logs/security-ci_YYYY-MM-DD_HH-MM-SS_UTC.log`; Windows uses the owned security log directory described in the test README. Entries use `[timestamp UTC] [LEVEL] [COMPONENT] Message`. Logs record setup, effective controls, scenario transitions, exit status, duration and cleanup; logging failures are explicit. Preserve failed-run diagnostics locally, and share only a reviewed redacted log when requesting support. There is no automatic log upload or retention service.
