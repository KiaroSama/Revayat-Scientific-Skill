# Security regression evidence

The separate `Security regressions` workflow has mandatory Linux and Windows tiers. It supplements ordinary portable/native document tests, CodeQL and dependency checks; none replaces a full source-and-runtime security engagement.

The finite scenario ledger is [tests/security/coverage.json](../tests/security/coverage.json), with fixture/control/containment documentation in [tests/security/README.md](../tests/security/README.md). It covers package relationship case identity, output links including native Windows/Python 3.11 junctions, shared HTML parser work admission across callers, and bounded TeX output observations. Independent WindowsBase OPC observation is not a claim about Microsoft Word behavior.

Prepared runtimes and trusted kernel probes precede reviewed document/helper execution. Windows authority checks protect the target, toolchain, parent-owned paths, scratch-root boundary and volume/quota controls. A unique CI-owned AppContainer profile is resolved through native APIs; its real filesystem and virtual-registry storage must be sealed before admission, tested for mutation denial and deleted during owned cleanup. Profile registration does not authorize writable off-scratch storage. Registry sealing must preserve read access while independently denying value writes, subkey creation, deletion, DACL changes and ownership changes; composite write-rights masks cannot be treated as mutation-only. Exact final-token open-only positive/negative controls precede resume, and matching stored descriptors alone are not effective-access evidence. Primary, duplicate and actual impersonating-thread LPAC context must agree, with LPAC established from its exact active native security attribute rather than unsupported token-query enum presence; the old read-negative fixture withholds package read-control allowance rather than assuming a package deny overrides an allow. Required API and fresh-open controls still reject every unexpected result or overgranted handle. Corrected registry DACLs are persisted per retained key with native DACL-only selection; granted descriptor rights and unchanged owner, group and integrity label are verified, followed by strict protected-DACL readback. No privilege restoration or fallback reopen is permitted. A child changing permissions on its own scratch file is not an escape: protected-creator and owner-selection controls must still prove that no protected resource or storage limit can be bypassed. Restricted-primary-token construction must remove Administrators ownership eligibility before LPAC admission; the actual suspended worker and descendants are checked again, and a native owner-assignment negative control must reject that identity even on a private file with `WRITE_OWNER`. Deny-only attributes alone do not satisfy this gate, and every remaining owner still requires a finite persisted quota. This construction remains a candidate until exact-revision hosted controls pass. Access-checked query denial on the worker's own process/thread is repaired only on those two objects, using its exact user plus existing package grant; same-token negative/positive controls and unchanged owner/group/integrity-label readback precede resume. This does not widen protected-storage access or establish a unique DLL initialization cause. Logical per-owner quota and physical aggregate capacity are verified separately, including sparse-file cases. Any missing isolation control fails closed, without executing the target phase. Required native cases cannot be converted into green skips. Tiny authored fixtures and dummy sentinels are the only test data; no credentials, deployed endpoints, stress payloads or real user manuscripts are needed.

## Evidence boundaries

- A requested container option is not an observed kernel control.
- A mock reparse attribute is not a native junction result.
- A case-insensitive package API is not proof of every Office consumer.
- An outer scratch quota is not production TeX output-bind quota.
- A mechanical result, artifact hash or clean CI is not user consent or semantic translation approval.

A bounded native startup trace of fixed trusted Python `-c pass` is diagnostic phase evidence only. It uses the same isolation settings and no target imports; normal undebugged kernel preflight remains the sole admission gate. A fixed no-CRT native `ExitProcess(0)` fixture provides an image-independent differential under those same controls; existing hosted compiler tools, bounded PE/import validation and a read-only seal precede its launch. Manifest generation is explicitly disabled for this fixed fixture, both known external manifest names must be absent before/after building and before launch, and its PE resource directory must be empty. A collision is refused without deleting existing entries. These checks qualify the fixture's minimal dependency contract, not the startup failure's cause; Python and target manifests remain unchanged. This diagnostic cannot replace Python 3.11 or admit target code. Debugger-altered behavior, either diagnostic exit or a last-loaded DLL never establishes containment or a unique initialization cause. A failed profile-access control can also record bounded API-handle granted-rights and same-mask fresh-open metadata; native query failure remains unknown, and these diagnostics never change the rejected control's outcome.

Owner-approved Loader Snaps may add detailed startup diagnostics only for the fixed trusted native fixture on a disposable hosted Windows runner. Its per-image setting and ownership marker are committed atomically; an existing key is never overwritten. Normal and outer interrupted cleanup qualify and transactionally delete only exact owned state, then verify absence before Python phases. Only bounded debug-string event bytes from that fixture may be read, with fixed allowlisted routine/module/status output; raw messages, paths, addresses and identities are never logged. Time/event/output ceilings stay unchanged. Configuration, parsing or cleanup failures never admit target code, and no local native diagnostic or sandbox permission relaxation is implied.

A separate fixed-native-only startup observation may summarize the suspended token's default new-object ACL after the existing admission preparations. Read-only queries and allocation-qualified ACL/ACE parsing emit only bounded category/count/mask metadata, distinguishing null, empty and unrecognized ACLs. No token or object permissions change, and this summary is neither an effective-access check nor evidence of the failed initializer's cause. Python and target execution remain behind the unchanged undebugged preflight.

Explicitly approved hardware diagnosis may observe fixed KernelBase initialization and `CsrClientConnectToServer` entry/return outcomes only in the fixed hosted native fixture. The fixed CSR connection observation replaces the earlier event-creation probe; it adds no routine selector or extra slot. Only the bounded entry `server_id` and paired raw `native_status` are recorded, not connection strings, buffers, ports or object names. Connection entry and return must remain inside the active initializer attach frame; an initializer return with an outstanding connection return is inconclusive before a qualified result is emitted. Reference prototypes justify scalar labels, not a current Windows internal-ABI guarantee or a permission repair. The existing debug-event controller uses temporary execution breakpoints on its owned creator thread, with verified OS-image provenance and bounded return-address reads. Only debugger registers change; code, PEB, arguments, results, general/control registers and sandbox permissions do not. Live stopped-thread cleanup restores the original diagnostic register state; a running timeout or destroyed thread uses verified owned termination instead of an invalid restoration attempt. Fixed scalar output contains no addresses or stack data. Debug-register ownership failures report only equality booleans and status/control bits; destruction failures distinguish EXIT receipt, retained-handle presence and the zero-time wait result. The original operation error and all cleanup errors are retained after every owned cleanup phase is attempted. These fields do not relax register ownership or extend deadlines. Pairing ambiguity or debugger-altered behavior remains inconclusive, and ordinary undebugged admission is unchanged. Trap attribution is distinct from configuration readback: only the exact creator, enabled owned instruction location and sole owned breakpoint cause can be handled, with foreign causes, bus-lock state, advanced controls and unsupported payload shapes refused. The architectural fixed DR7 bit is checked only at the trap stage; immediate setter/readback and restoration remain raw-exact. Raw RTM and bus-lock indicators are preserved separately at entry and return with unknown transaction context, never called inactive or normalized. The current instruction breakpoint is removed before continuation; exact return address and stack-frame pairing are mandatory.

A separately authorized hosted debugger control uses one immutable no-CRT trusted executable with a single byte-qualified exported site. It is built before runtime read-only sealing and run once afterward, before the unchanged LPAC phases. Only its owned creator-thread DR0 breakpoint is configured; bounded baseline, post-set/readback and hit status fields precede strict rejection. No status normalization, stack read, code/PEB/general-register/permission change or unrestricted executable selector is permitted. Unknown transitions remain inconclusive and nonzero after exhaustive cleanup. Cleanup records a process-termination request only after native success and does not repeat that successful request; failed requests retain their original errors and remain retryable. Job termination and continued EXIT, zero active processes and a signaled independent handle are still required: a successful termination request alone is not destruction evidence. Site bytes do not establish the surrounding transaction context, and trusted-host observations do not prove LPAC admission or initializer causality.

Only the exact tested revision, actual prerequisite observations, load-bearing positive/negative assertions and owned cleanup support a completion claim. Source-audit hypotheses remain unresolved until their decisive facts are observed or independently refuted. All limits must be named in the job/report rather than hidden by `continue-on-error`.

## Diagnostic logs

Parent controllers write one UTF-8 UTC log per run, without document bodies or secret values. Linux uses `logs/security-ci_YYYY-MM-DD_HH-MM-SS_UTC.log`; Windows uses the owned security log directory described in the test README. Entries use `[timestamp UTC] [LEVEL] [COMPONENT] Message`. Logs record setup, effective controls, scenario transitions, exit status, duration and cleanup; logging failures are explicit. Preserve failed-run diagnostics locally, and share only a reviewed redacted log when requesting support. There is no automatic log upload or retention service.
