# Bounded security regression tiers

These authored tests address specific source-audit hypotheses, not every possible vulnerability or container escape. `coverage.json` binds the exact scenarios and explicitly excludes Microsoft Word, external agent consent/provenance and real manuscript fidelity.

## Execution order

Manually dispatch the main `CI` workflow on the completed revision with the full base commit SHA. Its same-revision reusable security, CodeQL and dependency-review jobs run alongside the original checks; no push, PR or schedule starts a batch. The security tier prepares existing runtime dependencies outside the reviewed-code phase. Each required job then proves effective kernel controls before importing target helpers or processing fixtures. Missing controls fail the job; there are no successful prerequisite skips or unrestricted fallbacks.

- Linux uses a read-only prepared image/target, no network, non-root identity, dropped capabilities, no-new-privileges, CPU/memory/PID limits, per-file limits and bounded scratch tmpfs. The trusted image-owned probe checks environment equality, mount write refusal, namespace/cgroup/ulimit values, permitted scratch and sparse per-file rejection. Only fixed scenario scripts execute after the probe.
- Windows requires real Python 3.11, LPAC with no capabilities, a uniquely owned AppContainer profile whose actual filesystem and virtual-registry storage are sealed before worker admission, read-only copied runtime/target ACLs, explicit safe environment, Job Object ownership/resource bounds and a uniquely created disposable NTFS virtual disk. Profile mutation is checked at its real locations, and owned-profile deletion is part of normal and timeout cleanup. Registry sealing preserves read access and separately denies value writes, subkey creation, deletion, DACL changes and ownership changes. Exact final-token open-only old-deny/new-read-positive controls and individual mutation-access denials precede resume; composite `WriteKey` includes read-control access and cannot implement a mutation-only deny. Bounded primary/duplicate/effective-thread checks qualify the same owned zero-capability LPAC context. LPAC requires an exact active `WIN://NOALLAPPPKG` UInt64 value of 1 through a fixed-size native attribute query; missing, disabled, malformed or unsupported observations fail closed. The old read-negative fixture withholds only package `READ_CONTROL` allowance; no package-deny precedence is inferred. Both API and fresh-open read/mutation controls remain strict, and successful handles must not carry mutation authority. The corrected seal uses native DACL-only persistence on each retained key, requires actual read-control/write-DACL handle rights and verifies owner/group/integrity-label preservation plus protected ordered-DACL readback; it never restores privileges or reopens with a fallback. Its 128 MiB physical capacity and 16 MiB per-owner logical quota are distinct limits; multiple owner entries do not imply a 16 MiB volume-wide quota. A restricted LUA primary-token candidate precedes LPAC construction; admission requires Administrators ownership eligibility to be absent in the base, actual suspended worker and descendants, plus a native Administrators-owner assignment denial on a private scratch file with `WRITE_OWNER`. Deny-only membership alone is not proof that ownership eligibility was removed. The suspended worker token's privileges and assignable owner identities are constrained and checked before resume, with finite quota entries for every remaining permitted owner and the default; no owner is omitted to tolerate quota failure. A same-token negative/positive control checks query access to the worker's own process/thread objects before resume; their DACL repair adds only the exact worker user alongside the existing package grant, with owner/group/integrity-label readback preserved. This grants no access to other processes or protected storage and is not proof of a unique DLL initialization cause. Protected-creator and owner-selection controls verify that private scratch permission changes cannot bypass logical quotas or modify protected target/runtime, scratch-root or volume controls. Native EOF and ordinary/sparse positive/negative cases distinguish an effective limit from a configured one. Trusted controls run before native junction/public-adapter and existing WindowsBase OPC cases. Contained workers and fixed descendants are detached from consoles rather than requesting windowless console allocation. They retain suspended creation, explicit standard handles and all isolation/Job settings. Trusted preflight and its token-child query actual console absence and require NUL input plus captured output/error pipes; successful output and every original kernel assertion remain mandatory. This differential requires hosted validation, not a source-only causal claim. A mocked attribute check is not native junction evidence.

## Fixtures and assertions

All fixtures are harmless authored scientific/document/package data. DOCX relationship cases preserve original bytes and prior-output sentinels; supported and external-data edits are controls. HTML finite depth/cardinality cases cover parser, Source, guard, assets, text order, resource policy, public lint and the actual render-worker admission entry. The renderer backend is mocked only for admission ordering: refused inputs never invoke it, ordinary nesting does. This is not full rendering verification. Output-link cases protect outside sentinels. TeX writes only two tiny public text files and an ordinary PDF; finite tmpfs reservation verifies the outer aggregate budget without exhausting the host volume.

The outer test sandbox's aggregate quota does **not** prove that production TeX's writable output bind has an aggregate quota. Production controls and actual consumer policy must be reported separately; tests never upgrade a hypothesis to a confirmed security result merely from configuration.

## Logs, bounds and cleanup

Linux parent logs are UTF-8 in `logs/security-ci_YYYY-MM-DD_HH-MM-SS_UTC.log`, collision-safe, with UTC timestamp/level/component fields. The worker logs inside owned scratch; no source bodies, credentials or private environment values are logged. Windows setup logs are UTF-8 per run under the owned security log directory. Initialization failure is explicit, and handlers close on every exit.

Linux diagnostics are capped at 1 MiB; child/container wall deadlines are 90/110 seconds with a 20-second parent idle bound plus owned cleanup. A separate fixed trusted Python `-I -B -c pass` startup diagnostic may observe native debugger events under the same LPAC/token/profile/quota/Job settings. Existing hosted MSVC/SDK tools build it under an explicit compiler environment; bounded PE checks require x64 console code, an executable entry and only `KERNEL32.ExitProcess` imports before read-only sealing and the same isolated launch. Existing entries, directories or reparse points cause refusal without deletion. Managed malformed-resource fixtures check this qualification; Python and target manifests are not altered. Visual Studio discovery receives only its validated Windows `ProgramData` location in addition to the fixed setup environment; compiler/linker and isolated-worker environments remain unchanged.
