# Bounded security regression tiers

These authored tests address specific source-audit hypotheses, not every possible vulnerability or container escape. `coverage.json` binds the exact scenarios and explicitly excludes Microsoft Word, external agent consent/provenance and real manuscript fidelity.

## Execution order

`Security regressions` prepares existing runtime dependencies outside the reviewed-code phase. Each required job then proves effective kernel controls before importing target helpers or processing fixtures. Missing controls fail the job; there are no successful prerequisite skips or unrestricted fallbacks.

- Linux uses a read-only prepared image/target, no network, non-root identity, dropped capabilities, no-new-privileges, CPU/memory/PID limits, per-file limits and bounded scratch tmpfs. The trusted image-owned probe checks environment equality, mount write refusal, namespace/cgroup/ulimit values, permitted scratch and sparse per-file rejection. Only fixed scenario scripts execute after the probe.
- Windows requires real Python 3.11, LPAC with no capabilities, a uniquely owned AppContainer profile whose actual filesystem and virtual-registry storage are sealed before worker admission, read-only copied runtime/target ACLs, explicit safe environment, Job Object ownership/resource bounds and a uniquely created disposable NTFS virtual disk. Profile mutation is checked at its real locations, and owned-profile deletion is part of normal and timeout cleanup. Registry sealing preserves read access and separately denies value writes, subkey creation, deletion, DACL changes and ownership changes. Exact final-token open-only old-deny/new-read-positive controls and individual mutation-access denials precede resume; composite `WriteKey` includes read-control access and cannot implement a mutation-only deny. Bounded primary/duplicate/effective-thread checks qualify the same owned zero-capability LPAC context. LPAC requires an exact active `WIN://NOALLAPPPKG` UInt64 value of 1 through a fixed-size native attribute query; missing, disabled, malformed or unsupported observations fail closed. The old read-negative fixture withholds only package `READ_CONTROL` allowance; no package-deny precedence is inferred. Both API and fresh-open read/mutation controls remain strict, and successful handles must not carry mutation authority. The corrected seal uses native DACL-only persistence on each retained key, requires actual read-control/write-DACL handle rights and verifies owner/group/integrity-label preservation plus protected ordered-DACL readback; it never restores privileges or reopens with a fallback. Its 128 MiB physical capacity and 16 MiB per-owner logical quota are distinct limits; multiple owner entries do not imply a 16 MiB volume-wide quota. A restricted LUA primary-token candidate precedes LPAC construction; admission requires Administrators ownership eligibility to be absent in the base, actual suspended worker and descendants, plus a native Administrators-owner assignment denial on a private scratch file with `WRITE_OWNER`. Deny-only membership alone is not proof that ownership eligibility was removed. The suspended worker token's privileges and assignable owner identities are constrained and checked before resume, with finite quota entries for every remaining permitted owner and the default; no owner is omitted to tolerate quota failure. A same-token negative/positive control checks query access to the worker's own process/thread objects before resume; their DACL repair adds only the exact worker user alongside the existing package grant, with owner/group/integrity-label readback preserved. This grants no access to other processes or protected storage and is not proof of a unique DLL initialization cause. Protected-creator and owner-selection controls verify that private scratch permission changes cannot bypass logical quotas or modify protected target/runtime, scratch-root or volume controls. Native EOF and ordinary/sparse positive/negative cases distinguish an effective limit from a configured one. Trusted controls run before native junction/public-adapter and existing WindowsBase OPC cases. A mocked attribute check is not native junction evidence.

## Fixtures and assertions

All fixtures are harmless authored scientific/document/package data. DOCX relationship cases preserve original bytes and prior-output sentinels; supported and external-data edits are controls. HTML finite depth/cardinality cases cover parser, Source, guard, assets, text order, resource policy, public lint and the actual render-worker admission entry. The renderer backend is mocked only for admission ordering: refused inputs never invoke it, ordinary nesting does. This is not full rendering verification. Output-link cases protect outside sentinels. TeX writes only two tiny public text files and an ordinary PDF; finite tmpfs reservation verifies the outer aggregate budget without exhausting the host volume.

The outer test sandbox's aggregate quota does **not** prove that production TeX's writable output bind has an aggregate quota. Production controls and actual consumer policy must be reported separately; tests never upgrade a hypothesis to a confirmed security result merely from configuration.

## Logs, bounds and cleanup

Linux parent logs are UTF-8 in `logs/security-ci_YYYY-MM-DD_HH-MM-SS_UTC.log`, collision-safe, with UTC timestamp/level/component fields. The worker logs inside owned scratch; no source bodies, credentials or private environment values are logged. Windows setup logs are UTF-8 per run under the owned security log directory. Initialization failure is explicit, and handlers close on every exit.

Linux diagnostics are capped at 1 MiB; child/container wall deadlines are 90/110 seconds with a 20-second parent idle bound plus owned cleanup. A separate fixed trusted Python `-I -B -c pass` startup diagnostic may observe native debugger events under the same LPAC/token/profile/quota/Job settings. It records bounded module labels and exception/exit metadata only, with a 10-second/128-event/64 KiB observation ceiling that starts once after all suspended gates and resume, plus bounded exit-event cleanup; it does not import target code or count as containment acceptance. A second fixed trusted native startup fixture calls only `ExitProcess(0)` without CRT or CLR dependencies. Existing hosted MSVC/SDK tools build it under an explicit compiler environment; bounded PE checks require x64 console code, an executable entry and only `KERNEL32.ExitProcess` imports before read-only sealing and the same isolated launch. The fixed fixture links with `/MANIFEST:NO`; both `startup-native.exe.manifest` and `startup-native.manifest` must be absent before/after building and before launch, and PE resource-directory RVA and size must both be zero. Existing entries, directories or reparse points cause refusal without deletion. Managed malformed-resource fixtures check this qualification; Python and target manifests are not altered. Visual Studio discovery receives only its validated Windows `ProgramData` location in addition to the fixed setup environment; compiler/linker and isolated-worker environments remain unchanged. No compiler installation or developer-shell environment is permitted. Its exit is differential diagnostic evidence, not a replacement for Python 3.11. Normal undebugged kernel preflight remains mandatory, and a last-loaded module is not proof of a failed DLL initializer. Windows compiler/setup execution is wrapped by a stdlib-only outer Job owner (300-second wall, 45-second idle, 1 MiB combined output); fixed cleanup has separate 30/15-second bounds. Individual native preparation tools have 60/20-second bounds. Native worker budgets are recorded and queried by its controller; required controls must be observed before the target phase. Cleanup touches only the exact label/name/ID or the uniquely created Windows disk/profile/job state. A failed profile-access negative control may append fixed-size handle-rights query and same-mask fresh-open metadata without changing its failure: unknown query status is not acceptance, and no registry values or key names are read into logs. Useful failed-run logs remain for diagnosis; disposable scratch is removed after termination.

The fixed native fixture may additionally use owner-approved per-image Loader Snaps on the disposable hosted runner. A bounded registry transaction publishes only a new owned setting with its exact marker and flag; collisions are refused without edits. Cleanup verifies and deletes only that owned leaf transactionally, closes handles and checks absence before Python startup/preflight; outer interrupted cleanup uses the retained intent receipt. Only this native diagnostic reads bounded debug-string event spans (at most 4096 bytes per event), with exact read counts and strict decoding. Output contains fixed allowlisted routine/module/status labels, never raw strings, paths, addresses, identities or stacks. Existing 10-second/128-event/64 KiB limits remain; unknown or failed diagnostics are not containment acceptance. No local native execution, extra capability/privilege, global diagnostic setting or target-memory inspection is authorized.
